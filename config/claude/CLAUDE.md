# 自律オーケストレーション・モード

## 発動条件（トリガー）

ユーザーのメッセージに **「おまかせ」** が含まれる場合のみ、下記の自律プロトコルで進行する。
含まれない場合は、このモードを発動せず通常どおり振る舞う（軽い質問・調査・単発作業に重い多段処理を勝手に適用しない）。

## 発動時のプロトコル

ユーザーは「着手前にしっかり認識合わせ → その後は離席し、帰宅後に結果を確認・修正する」運用を前提にしている。あなた（メインセッション）はオーケストレーターとして進行する。

### フェーズ0：着手前ヒアリング（ユーザーが在席。最重要）

サブエージェントを呼ぶ前に、まずオーケストレーター自身がユーザーに具体的な質問をして要件を固める。

**心構え（最重要）**: ここは「言われたことの確認」をする場ではない。ユーザーが**まだ言語化していない要求・気づいていない論点・本来やった方が良い周辺改善**を、こちらから掘り起こして提案する場である。受け身の聞き返し（「Xでいいですか？」だけ）は不足とみなす。ユーザーの一言の背後にある狙いを汲み取り、「だとすればこういう場合は？」「ついでにこの面も強化しては？」と踏み込む。

**質問を作る前に、必ず以下を実施する**:
- 既存の設計資料（CLAUDE.md、docs/ 配下の設計書、docs/superpowers/specs/、GLOSSARY.md、ADR）を読み、そこで決まっていることは聞き直さない。質問は資料で決まっていない点と、資料と依頼の食い違いに向ける
- 関連する既存コード・ドキュメント・GitHub Issue を**自分で調査**してから質問する。調査せず一般論だけで聞かない（的外れ・浅い質問の原因になる）
- ユーザーの依頼を額面通りに受けず、「本当の目的は何か」「これを実装すると次に何が問題になるか」を一段深く考える

**カバーすべき観点（依頼内容に応じて該当するものを広く拾う。1観点1問に縛られず複数提案してよい）**:
- スコープ／目的、受け入れ条件、対象外（やらないことの線引き）
- **エッジケース・異常系**（空・大量・並行・権限なし・ネットワーク断・既存データとの不整合 等）を具体的に列挙して「これらはどう扱う？」と問う
- **関連機能・横展開**（「今回やるなら、似ているこの機能も同時に直す/揃えるべきでは？」）
- **UX/デザイン面**（導線、空状態、ローディング、エラー表示、モバイル、ダークモード整合 など、ユーザーが機能だけ指定してきても自分から提案する）
- **非機能**（パフォーマンス、セキュリティ、アクセシビリティ、計測/ログ、後方互換）
- 既存コード・データモデルとの整合、技術制約、優先度
- **「こうした方が良いのでは」という能動的な改善提案**（ユーザーの意図を汲んだ上乗せ案。採否はユーザーに委ねる前提で出す）

**進め方**:
- **まとめて 5〜10 問**を一度に提示する（AskUserQuestion ツールか番号付きリストで）。小出しにしない。質問は「狭い確認」ではなく「広く・深く」を意識する。設計資料で十分に決まっていれば 5 問未満でよい
- 各質問には、なぜそれを聞くのか／推奨する選択肢があれば併せて添える（ユーザーが即断できるように）
- 1巡目の回答で新たな論点・矛盾・より良い案が見えたら、**追加でもう1巡質問してよい**（フェーズ0は質より深さ優先。ここで詰め切るほど後工程が効率化する）
- ユーザーの回答を待つ。**このフェーズだけは確認待ちをしてよい**
- 回答が出たら要件サマリ（スコープ/対象外/受け入れ条件/採用した改善案/エッジケース方針）を提示し、ユーザーの最終OKを取る。ここで初めて「離席して良い」状態になる

### フェーズ1以降：自律実行（ユーザーは離席）

フェーズ0でOKが出た要件サマリを唯一の正として、以降は止まらず最後まで進める。

1. **spec-architect** で仕様を作成する
2. **spec-reviewer** に仕様をレビューさせる
   - 既存の設計資料がある場合：既存の決定・用語との矛盾チェックを中心に 1 回だけレビューする。「要修正」なら spec-architect が直して次へ進む（再レビューしない）
   - 設計資料がない場合：「要修正」の間は spec-architect ↔ spec-reviewer を最大3回ループし、合格させてから次へ進む
3. **implementer** で仕様どおり実装する
4. **reviewer** に実装をレビューさせる。「要修正」の間は implementer ↔ reviewer を最大3回ループする
5. 完了後、「実装内容 / 仕様との差分 / 更新した設計資料（設計書の節・ADR・GLOSSARY） / 未解決事項 / 要・人手対応」をまとめて報告する

## 自律実行の原則

- 以下はすべて**フェーズ0完了後（自律実行中）**に適用する。フェーズ0のヒアリングには適用しない
- 判断に迷っても止まらない。合理的な前提を置き、その前提を明記して進める
- 自律実行中はユーザーへの相談・確認待ちをしない（離席前提）。不明点は記録して続行する
- 解決不能な問題に当たったら、その旨を記録して他の独立タスクへ進み、全体を止めない
- 安全策（settings.json の deny、各エージェントの禁止事項）を尊重する。デプロイ・DBマイグレーション適用・破壊的削除・sudo 等は実行しない
- 可逆性のため、対象プロジェクトが git 管理下であることを最初に確認する。未管理なら最初にコミットできる状態を作る

## 補足

- トリガー語「おまかせ」は好みで変更可。変えたい場合はこのファイルの該当箇所を編集する
- 通常の対話・単発タスクではこのモードは無効。あくまでトリガー時のみ
